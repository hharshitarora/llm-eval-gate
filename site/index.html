Did my triage agent just get better, or worse?

My incident-triage-agent reads a crash log and names the commit that caused it. Like any AI agent, it answers a little differently every time, so one try can't tell me whether a change helped. These are its evals: tests with known answers, each run several times, every answer graded, and the change blocked only if the scores dropped by more than normal run-to-run wobble.

STEP 1

Plant a bug, so the right answer is known.

A script builds a small code repository and slips a bug into one commit. Because it planted the bug itself, it knows exactly which commit broke things and who wrote it. Then it writes the crash log a real user would trigger.

Here, a teammate renamed a field on User, but the mailer still reads the old name.

For engineers: 12 generated repos with byte-reproducible commit IDs. CI rebuilds them and fails if one ID drifts. Harmless commits land after the bug, so "blame the latest commit" scores zero.

    STEP 2
    
    Give the agent the crash. Three times.
    
    
    The agent gets what an on-call engineer would get: the repository and the log. Nothing about the answer. Since its answer can change from run to run, every test runs three times.
    
    
    The agent reads the log, the code and its history, and names the commit it thinks caused the crash.
    
    
    For engineers: the agent runs as a separate process. The harness calls python -m triage --json and reads one JSON object; it never imports the agent, so grading a different agent is a 50-line adapter.
    
  
    
  
    
    
    the agent's answer, one run of the November version
    
  
    

    


    
  
    
    STEP 3
    
    Grade each answer.
    
    
    Most of the grading is plain comparison, no AI involved: is it the commit we planted, and is it the person who wrote it?
    
    
    Only the written explanation needs judgement. A second AI model compares it with the explanation written when the bug was planted, and that judge is itself checked against the plain facts on every run.
    
    
    For engineers: exact match on commit (7+ char prefix) and owner surname. Judge scores the mechanism 0 to 3. Confidence is graded too (Brier, ECE): an agent that says 90% should be right about 90% of the time.
    
  
    
  
    
    
    this test's grades, all three runsSeptember → November
      
  
      

      


      
  
      
    STEP 4
    
      Compare with last time, allowing for wobble.
      
    
      All twelve tests are combined into one score per check. Then the gate measures how far those scores move if you rerun the same agent unchanged. That is the wobble.
      
    
      A drop smaller than the wobble is luck, so it passes. A bigger drop, or any score under a hard minimum, blocks the change.
      
    
      Switch to the broken agent to see a block.
      
    
      For engineers: wobble comes from a bootstrap that resamples whole tests. Allowed drop = max(policy minimum, wobble now + wobble last time). Exit code 0 or 1, so CI can block the merge.

cd llm-eval-gate
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt

python -m evalgate build                         # the 12 test repos
python -m evalgate run                           # test agent, passes, exit 0
python -m evalgate run --adapter mock:degraded   # broken test agent, blocked, exit 1
